## 1. Recommended first ERCOT-area retail utility

**CenterPoint Energy Houston Electric — commercial secondary-voltage
delivery service.**

Reasons:

- It is the delivery utility for the Houston load zone, matching the already
  configured `ercot_houston_hub`, so the wholesale price source and the
  delivery tariff describe the same physical site.
- ERCOT delivery tariffs are regulated and filed with the PUCT, so an
  authoritative, citable source document exists — the same property that made
  the PG&E work verifiable.
- CenterPoint is delivery-only. A Texas commercial site is therefore
  **TDU delivery tariff + a competitive retail energy contract**, which the
  repo can represent as two pieces rather than one schedule.

**Important consequence:** a CenterPoint tariff object must never be called
an "ERCOT tariff". The market operator sets no retail rates.

## 2. Recommended first PJM-area retail utility

**PECO Energy — commercial general service with demand**, with **Duquesne
Light** as the alternate.

The honest position first: **PJM Western Hub is a trading reference point,
not a service territory.** No utility "belongs" to it. Any pairing we choose

Given that, the criteria pull in different directions:

| Candidate | Source quality | Hub relevance | Commercial structure |
|---|---|---|---|
| **PECO** | High — PA PUC filings, published PDFs | Weak (eastern PA, PECO zone) | Demand-metered commercial classes with TOU options |
| **Duquesne Light** | Moderate | **Best** — Pittsburgh, western PA | Smaller commercial book |
| BGE | High | Weak (Maryland) | Strong commercial TOU |

**Recommendation: PECO**, because source quality and a demand-metered
commercial class matter more for the modelling work than geographic fidelity

## 3. Can the billing model represent them?

Partly. Verified capabilities of `TariffDefinition` today:

| Can represent | Cannot represent |
|---|---|
| Daily or monthly customer charge (one flat value) | Seasonal or tiered customer charge |
| TOU energy periods by hour, season, month, priority | **Day-of-week restriction** — `TOUPeriod` has no `days` field |
| Demand components on MAXIMUM / PEAK_PERIOD / PART_PEAK_PERIOD basis, optionally per season | Demand measured over an arbitrary hour window |
| Export rule (single rate, or explicitly not modelled) | Tiered or block rates on energy or demand |
| Voltage class, customer class, service type, effective dating | Separate rider or surcharge line items |

The energy and demand skeleton will carry a TDU or PECO schedule. The gaps
below are what will bite.

## 4. Charges the model cannot yet represent

Ranked by how likely each is to appear in the two chosen schedules.

1. **Weekday-only peak periods.** `billing.TOUPeriod` has no day-of-week
   field, while `signal_pipeline.price_sources.TimeOfUsePeriod` already has
   `days` (Monday 0 – Sunday 6). The codebase is inconsistent, and PG&E only
   hid it because its B-series applies "every day, including weekends and
   holidays". Most other commercial TOU schedules do not. **Prerequisite, not
   a nice-to-have.**
2. **Holidays.** Same root cause; already recorded in CLAUDE.md as the reason
   `price_sources.py` prices a holiday at its weekday rate.
3. **Ratchet demand.** Commercial tariffs commonly bill
   `max(current month, ratchet_pct x highest demand in the last 11 months)`.
   `calculate_demand_peak` computes `max(previous_peak_kw, simulated)` — the
   *mechanism* fits, but there is no ratchet percentage, no 11-month lookback
   and no place to store the history. Today `previous_peak_kw` means "peak
   already set earlier in this billing period", which is a different rule.
4. **ERCOT 4CP transmission.** Large Texas customers are allocated
   transmission cost by their demand during the four 15-minute ERCOT
   *system* peaks in June–September. That basis depends on system load, not
   customer load, and nothing in `DemandChargeBasis` can express it. It is
   also the single largest driver of commercial battery economics in ERCOT,
   so modelling CenterPoint without it will understate storage value
   substantially. **Do not attempt it this week** — flag it, size it, and
   plan it properly.
5. **Riders and surcharges** as separate line items (transmission cost
   recovery, energy efficiency cost recovery, nuclear decommissioning, etc.).
   Today they can only be folded into a blended rate, which loses the
   itemisation a real bill shows.
6. **Minimum bill / minimum demand**, **power factor adjustment**, and
   **reactive (kVAR) charges** — none representable.
7. **Time-windowed demand charges** (the already-known B1-ST blocker).

**Plan accordingly:** this week models the energy and demand skeleton
correctly and records every unrepresented rider in `notes`, in the same style
the PG&E tariffs already use. That is honest and useful; pretending otherwise
is what the repo's design deliberately prevents.

## 5. Realistic PV modelling approach

`WeatherDerivedPVConfiguration` already exists and validates `latitude`,
`longitude`, `rated_pv_capacity_kw`, `tilt_degrees`, `azimuth_degrees`,
`inverter_efficiency` and `system_losses_fraction`. Only the irradiance
provider and the model are missing.

**Why this matters.** Measured today: `SyntheticPV` produces *identical*
output on 21 June and 21 December — 85.00 kW peak, 703.3 kWh, 13.0 h of
daylight, both days. It has no declination, no weather and no shading. Since
demand charges are set by the summer peak, no annual bill or sizing number
computed from it is meaningful.

**Weather source: Open-Meteo.** No API key, free for non-commercial use,
returns shortwave radiation (GHI) plus direct and diffuse components *and*
2 m air temperature from one request — the same call the load model needs in
§6. PVGIS is the fallback if a typical-meteorological-year is preferred over
a specific historical year.

**Dependencies: none new.** Implement NOAA solar position and a fixed-tilt
plane-of-array transposition in numpy inside `src/profiles/`. `pvlib` is the
obvious alternative but adds a heavyweight dependency to a project that
already suffers from the system-Python/venv split described in CLAUDE.md.
Solar declination, hour angle and an isotropic-sky transposition are roughly
100 lines and directly testable against published values. If accuracy later
demands Perez transposition or a cell-temperature model, revisit then.

**Timezone and DST.** Solar position must be computed from **UTC instants**
derived from the tz-aware `IntervalIndex`, never from local wall-clock hours.
Note that today's `SyntheticPV` uses `timestamps.hour`, i.e. wall-clock, so
its "solar noon" silently shifts by an hour across a DST boundary. The new
model must not inherit that. Interval counts continue to come from the
generated index, never `days * 96`.

**Output contract unchanged:** `build_pv_available_kw` returns
`pv_available_kw` — AC power *available* at the inverter output before any
curtailment. This keeps the distinction that makes `MeasuredInverterPV`
raise, and keeps `allocate_surplus` meaningful.

**Offline and reproducible testing.** Commit one small weather fixture under
`data/weather/` (one year hourly for the demo site is a few hundred kB as
CSV). Tests read the fixture; the live fetch path is exercised only through a
`monkeypatch`ed client, matching how `test_signal_providers.py` already mocks
CAISO, ERCOT and PJM. Runtime fetches reuse the existing `cache_directory`
mechanism in `signal_loader.py`. **No test touches the network or needs a
secret.**

Acceptance: December/June energy ratio and annual kWh per kW installed land
in a defensible range for the site's latitude, and solar noon tracks
correctly either side of a DST transition.

## 6. Realistic commercial load modelling approach

Measured today: `SyntheticLoad` returns *identical* profiles for mid-January
and mid-July — 100.00 kW peak, 1329.0 kWh both days. It is a 24-value hourly
archetype shape with a weekend factor and optional noise, and has no
temperature response, so it cannot produce a summer cooling peak.

**Archetypes: start with three** — `office`, `retail`, `school`. All three
already exist in `BuildingArchetype`; this is a commercial-focused subset of
the six, not new enum members. `industrial` is deliberately excluded because
its load is process-driven rather than weather-driven.

**Weekday/weekend** behaviour already exists via `_WEEKEND_FACTORS` and is
kept. **Seasonal behaviour** is the new part: split the shape into a
base/process component and an HVAC component driven by cooling and heating
degree hours about a per-archetype balance-point temperature, using the same
Open-Meteo temperature series as §5. This is what produces a summer peak, and
therefore what makes the demand-charge economics real.

**Normalization**: keep both existing `LoadScaling` modes. Peak-kW scaling
must normalise against the *annual* peak once seasonality exists, otherwise a
winter-only horizon rescales to the wrong level — this is a behaviour change
to call out and test explicitly.

**Stochastic variation**: `SyntheticLoad` already takes `random_seed` and
uses `np.random.default_rng`. Keep it; every profile must be exactly
reproducible from its configuration.

**Offline sample datasets**: commit one year of hourly temperature for the
demo site alongside the irradiance fixture. Calibrate archetype shapes
against the DOE/NREL Commercial Reference Buildings, which are public domain
— and record in `notes` that the shapes are *archetypes calibrated to* those
references, not measured data.

## 7. Proposed public interfaces to `src/simulation/`

Offered for agreement before either lane integrates. Backend implements;
Codex consumes.

```python
# src/profiles/site.py  (new, backend-owned)
@dataclass(frozen=True)
class SiteLocation:
    """Where the modelled site is, for weather and solar geometry."""
    latitude: float
    longitude: float
    timezone: str              # IANA name, must match the analysis timezone
    elevation_m: float = 0.0

# src/signal_pipeline/weather.py  (new, backend-owned)
@dataclass(frozen=True)
class WeatherSeries:
    """Hourly irradiance and temperature aligned to an interval index."""
    ghi_w_m2: pd.Series
    dni_w_m2: pd.Series
    dhi_w_m2: pd.Series
    temperature_c: pd.Series
    source: str                # provider id, for provenance in results

def load_weather(
    location: SiteLocation,
    interval_index: IntervalIndex,
    *,
    cache_directory: str | Path | None = None,
) -> WeatherSeries: ...

# src/profiles/pv_sources.py  (existing class, becomes functional)
WeatherDerivedPV(configuration=WeatherDerivedPVConfiguration(...),
                 weather=WeatherSeries)      # no longer raises

# src/profiles/load_sources.py  (new class alongside SyntheticLoad)
@dataclass
class WeatherResponsiveLoad(LoadProfileSource):
    archetype: BuildingArchetype
    scaling: LoadScaling
    peak_kw: float | None = None
    annual_energy_kWh: float | None = None
    temperature_c: pd.Series | None = None    # None -> no HVAC response
    random_seed: int | None = None
```

The GUI contract is then small: the interface layer supplies a
`SiteLocation`, and `retail_tariff_ids_for_region` gains entries for the two
new regions. **No existing signature changes**, so Codex's in-flight work
cannot be broken by this.
